# Claustra

Claustra is a passkey-first OpenID Connect provider for personal services. It supports public passkey registration, optional consented profile claims, verified-email recovery, administrator-managed clients, per-service email allowlists, pairwise subject identifiers, and a Caddy forward-auth adapter.

The implementation follows the behavior in [claustra-design.md](./claustra-design.md). The interface is a dark, purple-accented set of server-rendered pages: sign-in and consent, an account page for profile, passkeys, sessions, and connected apps, and an administrator page for clients, forward-auth hosts, and roles. All styling is served from the origin, so the strict Content-Security-Policy needs no exceptions.

## Implemented protocol

- OpenID Connect Authorization Code Flow
- mandatory PKCE `S256`, `state`, and `nonce`
- confidential server-backed clients using `client_secret_basic`
- pairwise `sub` per user and client
- `openid`, `profile`, and `email` scopes
- signed five-minute RS256 ID tokens and rotating JWKS overlap
- opaque fifteen-minute access tokens for UserInfo and avatars
- discovery, authorization-server metadata, UserInfo, JWKS, and revocation
- exact HTTPS redirect-URI matching

Implicit flow, refresh tokens, browser-only/native clients, dynamic client registration, device authorization, and general API delegation are deliberately absent.

## Local development

Prerequisites: Go 1.25+, Postgres 17+, and a browser with WebAuthn support.

```sh
docker compose up -d postgres mailpit
go run ./cmd/claustra keygen ./development-signing-key.pem

export CLAUSTRA_ISSUER=http://127.0.0.1:13002
export CLAUSTRA_RP_ID=127.0.0.1
export CLAUSTRA_LISTEN_ADDR=127.0.0.1:13002
export CLAUSTRA_DATABASE_URL='postgres://claustra:development-only@127.0.0.1:5432/claustra?sslmode=disable'
export CLAUSTRA_SIGNING_KEY_FILE="$PWD/development-signing-key.pem"
export CLAUSTRA_SECURE_COOKIES=false
export CLAUSTRA_SMTP_HOST=127.0.0.1
export CLAUSTRA_SMTP_PORT=1025
export CLAUSTRA_SMTP_FROM=claustra@localhost
export CLAUSTRA_SMTP_STARTTLS=false

go run ./cmd/claustra serve
```

Create the first administrator in another shell. The URL is valid for 15 minutes and only while no administrator exists:

```sh
go run ./cmd/claustra bootstrap
```

Mailpit is available at `http://127.0.0.1:8025` during development.

## Configuration

Required variables:

| Variable | Purpose |
| --- | --- |
| `CLAUSTRA_DATABASE_URL` | Postgres connection URL |
| `CLAUSTRA_SIGNING_KEY_FILE` | Active RSA private key generated by `claustra keygen` |

Important optional variables include `CLAUSTRA_ISSUER`, `CLAUSTRA_RP_ID`, `CLAUSTRA_LISTEN_ADDR`, `CLAUSTRA_PREVIOUS_SIGNING_KEY_FILES`, and the `CLAUSTRA_SMTP_*` family. Production defaults use `https://claustra.marcusson.dev`, `127.0.0.1:13002`, secure cookies, 30-day idle sessions, and 90-day absolute sessions.

For signing-key rotation, generate a new key, retain the former key in `CLAUSTRA_PREVIOUS_SIGNING_KEY_FILES`, switch `CLAUSTRA_SIGNING_KEY_FILE`, and restart. Keep former keys in JWKS for longer than the five-minute ID-token lifetime.

## Service access

Registration is public, so holding a Claustra account is not by itself permission
to use a service. Every OIDC client and every forward-auth host carries an access
policy:

| Policy | Who gets in |
| --- | --- |
| `allowlist` | only accounts holding a **verified** email address listed against that service |
| `open` | any active Claustra account |

New clients and hosts default to `allowlist` with an empty list, so a service that
is registered and then forgotten admits nobody. A policy left unset by a caller
resolves to `allowlist` for the same reason. Entries that predate this feature
were migrated to `open` to preserve the behaviour they were deployed with;
tighten them from `/admin/clients`.

Only verified addresses count. An unverified address is self-asserted, and
honouring it would let anyone reach a gated service by claiming an address they
do not control. An account with no verified address can never satisfy an
allowlist.

The check runs at `/authorize`, again at the consent POST, and once more when the
authorization code is redeemed, so an address removed mid-flight cannot buy a
token. Forward-auth re-checks on every proxied request rather than trusting the
cookie it minted, and removing an address revokes the access tokens and
forward-auth sessions it was holding.

A signed-in user who is not on the list gets a Claustra page naming the service
and the address that was checked, rather than a bounce back to the relying party
— which would only redirect them here again.

## Registering an OIDC client

Sign in as an administrator and open `/admin/clients`. Choose who may sign in — an allowlist of addresses, or any Claustra account — and Claustra displays a new client secret exactly once. A client must:

1. discover Claustra from `/.well-known/openid-configuration`;
2. create `state`, `nonce`, and a PKCE verifier/challenge;
3. send `response_type=code`, `scope=openid`, and an exact registered redirect URI;
4. exchange the returned code at `/token` with HTTP Basic client authentication and the PKCE verifier;
5. validate ID-token signature, issuer, audience, expiry, and nonce;
6. create its own local session rather than retaining the ID token as a session cookie.

## Sign-in button

Services that use Claustra get a drop-in button. Copy [`claustra-button.css`](./internal/server/styles.go) (also served at `/static/claustra-button.css`) into the service, then link the anchor at whatever route starts that service's authorization request:

```html
<a class="claustra-login" href="/auth/claustra/start">
  <span class="claustra-login__label">Log in with Claustra</span>
  <svg class="claustra-login__lock" viewBox="0 0 24 24" fill="none" stroke="currentColor"
       stroke-width="2" stroke-linecap="round" stroke-linejoin="round" aria-hidden="true">
    <rect x="3" y="11" width="18" height="11" rx="2.5"/>
    <path d="M7 11V7a5 5 0 0 1 9.9-1"/>
    <circle cx="12" cy="16.5" r="1.1" fill="currentColor" stroke="none"/>
  </svg>
</a>
```

The stylesheet is self-contained and carries no fonts, scripts, or network requests; its animation stops under `prefers-reduced-motion`. Copying it is preferred over linking, so a service's sign-in page never depends on Claustra serving assets. The administrator page renders a live preview and the same snippet.

## Caddy forward-auth

Register each protected hostname under the administrator page, then use:

```caddyfile
(claustra) {
  handle /_claustra/* {
    reverse_proxy http://127.0.0.1:13002
  }
  handle {
    forward_auth http://127.0.0.1:13002 {
      uri /forward-auth/verify
      copy_headers X-Claustra-User X-Claustra-Sub
    }
    reverse_proxy {args[0]}
  }
}
```

The upstream must be reachable only through Caddy, and Caddy must replace caller-supplied identity headers. Exempt non-browser API paths before importing the snippet.

## NixOS

The flake exports `nixosModules.default` and a package. A minimal deployment is:

```nix
{
  inputs.claustra.url = "github:olivermarcusson/claustra";
  imports = [ inputs.claustra.nixosModules.default ];
  services.claustra = {
    enable = true;
    backup.enable = true;
    backup.ageRecipient = "age1...";
    environmentFile = "/run/secrets/claustra.env";
  };
}
```

The module provisions a local Postgres database by default, generates the initial signing key in `/var/lib/claustra`, runs behind Caddy, applies systemd hardening, and retains exactly seven encrypted daily backups. The environment file should be outside the Nix store and readable by the `claustra` service account.

After restoring an old database, invalidate ephemeral authentication state before returning the service to traffic:

```sh
claustra invalidate-restored-state
```

## Testing

```sh
go test -race ./...
TEST_DATABASE_URL='postgres://...' go test -v ./...
```

Database-backed tests are skipped when `TEST_DATABASE_URL` is unset.

## Security status

Claustra is security-sensitive software. Before exposing it to users, run independent review, exercise SMTP recovery and WebAuthn against the production origin, test backup restoration, and run the OpenID conformance suite. Do not deploy with development cookie settings, development SMTP, or the Compose password.
